# 3.3 Hex Cells Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** When finalize-drive counts a drive, it records the H3 resolution-9 cells the driver explored in `explored_cells`.
This is atomic with "drive counted". It returns "+N new cells" to the app, and the recap shows it.

**Architecture:**
- **Cells rule:** a pure rule in `src/lib/cells.ts` turns the cleaned, moving points into a sorted list of unique cells. It
  fills gaps of 2 km or less with `gridPathCells`. It is shared with the Edge Function by `npm run sync:edge`; Deno resolves
  `h3-js` through a function-level `deno.json`.
- **Atomic save:** a new SQL function `public.finalize_counted_drive(...)`, callable only by the service role, does everything
  in one transaction:
  - the compare-and-set `uploading → processed` on `drives`
  - the `drive_private` upsert
  - the cell insert (`on conflict do nothing`, so the first drive keeps a cell)
  - writing `drives.new_cells`

  A failed cell write therefore can never leave a counted drive without cells, and the app's retry stays idempotent.

**Tech Stack:**
- h3-js 4.5.0 (already a dependency; on the Edge it is `npm:h3-js@4.5.0`)
- Supabase Postgres plpgsql + pgTAP
- Deno Edge Function
- Node test runner (`npm test`)
- Expo Router UI

**Spec:** this plan's "Design" section (agreed with PS, 2026-11-12, Opus planning session). Also read
`docs/superpowers/specs/2026-11-10-drive-upload-finalize-design.md` (how finalize-drive works) and handoff.md "Spike 3.0 result".

## Design (decided)
1. **Which points count:** the same cleaning as the drive stats.
   - Accuracy ≤ `CLEANING.maxAccuracyM` (25 m).
   - Drop teleports: implied speed from the last ACCEPTED point > `CLEANING.maxPlausibleKmh`.
   - Only MOVING points count. Speed is the chip speed when known, else the implied speed from the last accepted point, and it
     must be ≥ `CLEANING.stoppedBelowKmh` (3 km/h). A parked phone's GPS drift explores nothing.
2. **Gap fill:**
   - Between two consecutive moving points whose cells differ and which are ≤ 2,000 m apart (straight line): add
     `gridPathCells(a, b)`.
   - If they are farther apart, add only the two points' own cells, so a GPS jump earns no free cells.
   - If `gridPathCells` throws (rare, near pentagons), add only the two cells.
3. **Privacy zones do NOT trim cells.** Cells are owner-only (RLS "explored_cells: owner reads"), unlike the public route.
4. **"New" = first time ever** for that user. On conflict the existing row (its `first_drive_id`, `first_seen_at`) is kept.
   "This week" on the Explore map is a later map filter, not part of 3.3. `first_seen_at` = the drive's start time.
5. **Cap:** more than `CELLS.maxCellsPerDrive` = 20,000 cells means reject with `too_long`. This is impossible for a real drive
   within the 12 h limit: about 3,000 km ≈ 10k cells.
6. **Guests:** nothing in 3.3. Their fog comes from local drives on the phone in 3.4, which will reuse `driveCells`.
7. **Old counted drives:** no cells (no back-fill in 3.3). A one-off back-fill from the stored raw tracks is a possible later task.
8. **The app** shows a "New cells" tile on the recap for counted drives only, value in `c.primaryText` like design 10. It sits on
   the third tile row next to Top speed.
   - The Saving screen's "map cells" row stays hidden until 3.1 (XP).
   - Nothing on the HUD.

## Review Focus
1. **A drive that is retried after it was counted** (lost answer): the second call must return the same `newCells`, not 0 and not
   an error. `alreadyDecided` reads `drives.new_cells` (Task 4).
2. **Two overlapping drives** (the 23P01 exclusion constraint fires inside the SQL function): NO cells and NO `drive_private`
   row may survive, and the drive must end up `rejected: overlap`. The pgTAP test is in Task 3.
3. **A drive that only revisits known cells** returns 0 and shows "New cells 0". It must not be hidden or shown as null
   (Tasks 3 and 5).
4. **Parked with the app recording** (drift across a cell border) gives 0 cells (Task 1 test).
5. **A tunnel or dropout over 2 km** must not fill the straight line between, and one ≤ 2 km must fill it (Task 1 tests).

    - The cell at the gap's midpoint is included for 1.5 km and NOT included for 3 km.
  - `teleports and poor-accuracy points are ignored`
    - One point 0.5° away (with `speed` 10) and five points with `accuracy: 40`, placed 0.05° east.
    - Their cells are not in the result.
  - `output is sorted and unique, whatever the input order`
    - `driveCells([...pts].reverse())` deep-equals `driveCells(pts)`.

  - `points without a chip speed use the implied speed`: the 6 km drive with `speed: null` everywhere gives the same cells as
    with speeds.

### Task 3: Atomic save in the database (`finalize_counted_drive`)

**Files:**
- Create: `supabase/migrations/20261112130000_finalize_counted_drive.sql`
- Modify: `supabase/tests/rls_test.sql` (`plan(86)` becomes `plan(95)`, plus a new section before "PDPA")

**Interfaces:**
- Produces (SQL, called by Task 4 via `admin.rpc('finalize_counted_drive', {...})`):
  ```sql
  public.finalize_counted_drive(
    p_drive_id uuid, p_user_id uuid, p_started_at timestamptz, p_ended_at timestamptz,
    p_distance_m real, p_moving_s int, p_elapsed_s int, p_avg_moving_kmh real, p_avg_overall_kmh real,
    p_route text,          -- EWKT 'SRID=4326;LINESTRING(...)' or null
    p_track_path text, p_top_kmh real, p_raw_points int, p_flags jsonb,
    p_cells text[]
  ) returns int            -- new cells; NULL when the drive was no longer 'uploading' (someone else decided it)
  ```

- [ ] **Step 1: Write the migration.**
  - `language plpgsql`, `security invoker`, `set search_path = ''`. All names are schema-qualified (`public.`, `extensions.`).
  - **Order inside the function:**
    1. `update public.drives set status='processed', started_at, ended_at, the five stats, route = p_route::extensions.geography
       where id = p_drive_id and user_id = p_user_id and status = 'uploading' returning id into v_id`
    2. If `v_id is null`, return null.
    3. `insert into public.drive_private (drive_id, user_id, track_path, top_kmh, raw_points, flags) ... on conflict (drive_id)
       do update set` the same columns.
    4. `insert into public.explored_cells (user_id, h3_index, first_drive_id, first_seen_at) select p_user_id, c, p_drive_id,
       p_started_at from unnest(p_cells) as c on conflict (user_id, h3_index) do nothing`
    5. `get diagnostics v_new = row_count`
    6. `update public.drives set new_cells = v_new where id = p_drive_id`
    7. Return `v_new`.
  - A 23P01 from the exclusion constraint in step 1 must simply propagate: the whole call rolls back.
  - Then:
    ```sql
    revoke execute on function public.finalize_counted_drive(...) from public, anon, authenticated;
    grant execute ... to service_role;
    ```
  - Top comment: why (atomic with the counted drive, retry-safe), and "only the finalize-drive Edge Function calls this".
